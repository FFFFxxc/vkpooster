# Серверная автоматизация через пользовательский токен — дизайн

## Цель

Отложенные копии постов, комментарии и истории должны выполняться на Render без
запущенного Chrome. Фотографии копируемого поста должны загружаться в целевое
сообщество только в фактический момент выхода, чтобы время фотографии совпадало
со временем публикации. Токены сообществ временно исключаются из рабочих
сценариев и интерфейса. Карточка «Ожидания» хранит выбранные сообщества, время,
режим, текст и комментарий до отправки.

## Выбранный подход

Из трёх вариантов — локальная очередь Chrome, нативная отложка VK и очередь
Render — используется очередь Render для будущих постов. Локальная очередь
остаётся только для немедленной публикации и как резерв для комментария, если
сервер недоступен. Нативный `publish_date` больше не применяется к новым копиям
из «Ожиданий»: именно он вынуждал загружать фотографии заранее.

Пользовательский токен передаётся только по HTTPS в запросе, защищённом
`API_SECRET`, шифруется существующим AES-256-GCM vault с
`TOKEN_ENCRYPTION_KEY`, не логируется и не возвращается API. Каждый документ
получает собственные IV и authentication tag.

## Компоненты

### Серверные посты

`ScheduledPost` хранит исходный `owner_id/post_id`, текст, режим, целевые
сообщества, время выхода, результаты, зашифрованный пользовательский токен и
данные комментария. Worker атомарно арендует одну задачу и обрабатывает только
одно сообщество за проход. Следующее сообщество допускается не раньше чем через
15 секунд. Это исключает параллельный шквал запросов с одного аккаунта.

В режиме копии worker в момент выхода заново читает исходный пост через
`wall.getById`, скачивает каждую фотографию по HTTPS, получает
`photos.getWallUploadServer`, сохраняет её через `photos.saveWallPhoto` и лишь
затем вызывает `wall.post` без `publish_date`. Видео, документы и аудио
переиспользуются как VK-вложения. В режиме репоста worker вызывает
`wall.repost` в фактическое время.

После успешного `wall.post` worker создаёт серверное задание комментария с тем
же токеном и рассчитанным временем. Результаты сохраняются по сообществам;
задачу можно отменить или повторить. Завершённые записи удаляются существующей
очисткой и TTL.

### Комментарии и истории

Поле входного API переименовывается с `groupToken` на `userToken`. Worker
комментариев вызывает `wall.createComment` с `from_group` и пользовательским
токеном. Истории выбирают сообщества из `vkr_user_groups` и передают тот же
`vk_token`; серверный story worker использует его для upload/save вызовов.

### Расширение

Новый будущий пост отправляется на `/api/scheduled-posts`. Немедленный пост
по-прежнему публикуется локально, после чего комментарий сначала ставится на
сервер через пользовательский токен. При недоступности Render комментарий
остаётся в локальной резервной очереди.

Секция токенов сообществ и переключатель режима комментариев удаляются из
popup. Список пабликов везде строится только из `vkr_user_groups`.
Существующее значение `vkr_group_tokens` не удаляется автоматически, но больше
не читается рабочими меню и не используется для публикации.

### «Ожидания»

Каждый элемент получает `draft` со следующими полями:

- `groups: number[]`;
- `mode: "copy" | "repost"`;
- `pubDateLocal: string` в формате `datetime-local`;
- `text: string`;
- `commentText: string`;
- `updatedAt: number`.

Форма сохраняет draft при каждом изменении и перед закрытием. Карточка показывает
названия выбранных пабликов и время, а кнопка «Открыть исходный пост в VK» и
кликабельный заголовок всегда открывают исходную стену. После успешной постановки
на сервер элемент удаляется из «Ожиданий».

## Ошибки и восстановление

- транспортные ошибки и VK 1/2/10 повторяются с ограниченным backoff;
- CAPTCHA, flood control, проверка входа и другие protective коды переводят
  задачу в `paused` без дальнейших запросов;
- неверный/истёкший токен завершает целевое сообщество ошибкой;
- повторный запрос с тем же `idempotencyKey` возвращает существующую задачу;
- публичные сериализаторы исключают все поля токена;
- отмена удаляет только ещё не опубликованные цели, уже вышедшие посты остаются
  в результатах;
- если сервер недоступен при создании будущего поста, карточка остаётся в
  «Ожиданиях» вместе с draft.

## Проверка

TDD покрывает: валидацию user token, отсутствие секретов в ответе, серверный
копирующий upload-поток, последовательный worker, комментарий через user token,
истории через user token, CRUD scheduled posts, отсутствие group-token UI и
сохранение/восстановление draft. Затем запускаются `npm run verify`, rollback на
отдельной копии и повторный smoke-тест восстановленного baseline.
